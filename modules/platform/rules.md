# Правила сервисов platform

Как устроен Go-сервис группы platform. Прочитай перед тем, как заводить сервис или писать в нём код.

## Структура

```
modules/platform/
├── rules.md
├── sqlc.yaml               конфиг sqlc для всех сервисов группы
├── local.env               переменные для локального запуска
├── .env                    личные переменные и секреты, не коммитится
├── internal/               общий код сервисов группы
│   ├── apperr/             ошибки
│   ├── httpx/              Echo, middleware, обработчик ошибок, запуск сервера, проверки здоровья
│   ├── logx/               логгер
│   ├── pg/                 пул соединений, транзакции, разбор ошибок Postgres
│   └── testutil/           общие помощники для тестов
└── s1-<сервис>/
    ├── main.go             вызывает run
    ├── app.go              run: собирает зависимости, запускает и останавливает сервис
    ├── config.go           Config
    ├── server.go           newServer: собирает Echo без запуска
    ├── routes.go           все маршруты сервиса
    ├── handler/
    ├── service/
    └── store/
        ├── queries/        SQL-запросы
        └── sqlc/           код, сгенерированный sqlc
```

sqlc берёт схему базы из `db/postgres/migrations/`.

## Правила

- Сервис делится на три слоя: handler, service, store.
- Handler разбирает и проверяет запрос, вызывает service и возвращает ответ.
- Service содержит бизнес-правила и открывает транзакции.
- Store — только SQL-запросы, код store генерирует sqlc.
- Модели OpenAPI используются в handler и service, в store не попадают.
- Модели sqlc используются в service и store, в handler не попадают.
- Модели OpenAPI и sqlc преобразуются друг в друга в service.
- Service возвращает ошибки из `internal/apperr`, в HTTP-коды их переводит общий обработчик ошибок.
- Контекст запроса передаётся во все слои.
- Сгенерированный sqlc код не коммитится.

## Точка входа

- `main.go` только вызывает `run` и завершает процесс при ошибке.
- `run` собирает зависимости, запускает сервис и останавливает его по сигналу.
- `newServer` собирает Echo без запуска сервера, интеграционные тесты используют его.
- Все маршруты сервиса регистрируются в `routes.go`.
- Зависимости передаются через конструкторы, без DI-фреймворков.
- Общий код запуска лежит в `internal`, в сервисе остаётся только своё.
- Фоновые задачи запускаются в `run` через `errgroup` и останавливаются вместе с сервером.

## Логи и ошибки

- Логи пишутся через `log/slog` в stdout в формате JSON.
- Уровень логов задаёт переменная `LOG_LEVEL`, по умолчанию `info`.
- Имена полей лога — по семантическим соглашениям OpenTelemetry.
- На каждый запрос — одна строка лога, ошибка пишется в ту же строку.
- Запросы к `/healthz` и `/readyz` не логируются.
- Store и service только возвращают ошибки, логирует их общий обработчик ошибок.
- При ошибке 5xx клиент получает `internal error`, подробности есть только в логе.
- `X-Request-ID` передаётся во все вызовы других сервисов.
- В логи не пишем токены, пароли, тексты сообщений и данные клиентов.

## Middleware

- Middleware подключает общая функция из `internal/httpx`, во всех сервисах одинаково.
- Порядок: RequestID, RequestLogger, Recover, BodyLimit, ContextTimeout.
- Тело запроса не больше 1 МБ, другой лимит задаётся только на отдельном маршруте.
- Таймаут запроса — 10 секунд.

## Конфигурация

- Конфигурация читается только из переменных окружения.
- Переменные читаются один раз при старте в `Config` через `caarlos0/env`.
- Без обязательной переменной сервис не запускается.
- В переменные выносится только то, что отличается между окружениями.
- Значения по умолчанию есть только у `PORT`, `S1_ENV` и `LOG_LEVEL`.
- Имена переменных пишутся заглавными буквами через подчёркивание.
- Локальные значения лежат в `local.env` и коммитятся, секреты и личные значения — в `.env`.
- Сервис сам не читает `local.env` и `.env`, их подключают Makefile или IDE.

## Тесты

- Тесты бывают трёх уровней: модульные, интеграционные и сквозные.
- Модульные тесты не ходят в базу и во внешние сервисы.
- Интеграционные тесты работают с настоящим Postgres, остальные зависимости подменяются фейками.
- Postgres для интеграционных тестов поднимается через testcontainers.
- Интеграционные тесты помечаются тегом сборки `integration`.
- Сквозные тесты проверяют развёрнутую систему на stage.
- Тесты лежат рядом с кодом, общие помощники — в `internal/testutil`.
- Каждый тест создаёт свои данные и не зависит от других тестов.
- Проверки пишутся через `testify/require`.
- Локально тесты запускаются командами `make test` и `make test-integration`.

## Стиль кода

- Комментарий — одно предложение о том, за что отвечает код, на русском.
- Если это видно из имени, комментарий не пишется.
- Код форматируется `gofmt` и `goimports`, импорты в три группы: стандартные, сторонние, свои.
- Линтер — `golangci-lint` с конфигом `.golangci.yml`, запускается `make lint`.
- Сгенерированные пакеты импортируются с псевдонимом: `dialogsapi`, `dialogsroutes`.
- Имя типа не повторяет имя пакета: `service.Client`, а не `service.ClientService`.
- Интерфейсы объявляются только для вызовов других сервисов, на стороне того, кто вызывает.
- Service работает с `*sqlc.Queries` напрямую, логику с базой проверяют интеграционные тесты.
- Ошибка оборачивается с контекстом: `fmt.Errorf("get client: %w", err)`.
- Без глобальных переменных, `init()` и `panic` в бизнес-логике.
- `ctx` — первый параметр и не хранится в структуре.
