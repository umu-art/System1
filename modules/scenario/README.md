# Сервисы сценариев

- `s1-workflow-validator` проверяет блоки по каталогу и управляет воркфлоу через `/v1/workflow`. Он хранит определения в `workflow_validator.workflows` и `workflow_validator.blocks`.
- `s1-workflow` запускает сохранённый граф через `/api/workflow/runs`. Он получает список блоков по HTTP, индексирует их по ID и сохраняет снимок графа и состояние в `workflow.runs`. Правка или удаление определения влияет на новые запуски. Текущий запуск продолжает исполнение по своему снимку.

При старте валидатор возвращает `serviceId` вместе с блоками. Исполнитель сохраняет его в `workflow.runs.service_id` и проверяет текущего владельца по `owners.services` при чтении запуска и обработке событий. При передаче сервиса новый владелец получает доступ к его истории и может продолжить ожидающие запуски, в том числе после удаления определения workflow.

В таблице `workflow.runs` колонка `current_block_id` указывает на блок ожидания или ошибки. При успешном завершении она равна `NULL`. Колонка `status` принимает значения `waiting_message` (ждём текст), `waiting_payment` (ждём исход платежа), `completed` (сценарий завершён) и `failed` (исполнение остановилось с ошибкой). В `variables` хранятся значения `input.*` и `state.*`, в `state` — результаты блоков, сообщения, принятые события и служебные данные. Исполнитель сохраняет их вместе при старте и при обработке события.

Один модуль Go подключает сгенерированные серверные интерфейсы и HTTP-клиент валидатора. Контракты находятся в [api/src](../../api/src), миграции — в [db/postgres/migrations](../../db/postgres/migrations).

## Локальный запуск

1. Примените миграции Flyway к базе Postgres. Для локального запуска нужен существующий владелец и связанный с ним сервис в `owners.owners` и `owners.services`.
2. Из корня репозитория выполните `python api/build.py --langs go`. В каждом из двух терминалов перейдите в `modules/scenario` и задайте `DATABASE_URL`.
3. Запустите валидатор и исполнитель в отдельных терминалах.

```sh
PORT=8081 go run ./s1-workflow-validator
```

```sh
PORT=8080 WORKFLOW_VALIDATOR_URL=http://127.0.0.1:8081 go run ./s1-workflow
```

При старте валидатор читает `../../api/src/workflow-blocks.schema.yaml` относительно рабочей папки. Для другого расположения задайте `WORKFLOW_CATALOG_PATH`. Оба процесса проверяют доступ к нужным таблицам через `/readyz`.

## Проверка через HTTP

Следующие команды используют тестового владельца по умолчанию (`00000000-0000-0000-0000-000000000001`). Для создания воркфлоу укажите ID существующего сервиса этого владельца. В тестовых данных платформы это `00000000-0000-0000-0000-000000000101`. На чистой БД сначала загрузите тестового владельца и его сервис. Если сервис ещё не создан, POST вернёт 404. Для проверки с другим владельцем добавьте `?userId=<UUID владельца>` к каждому запросу и используйте его сервис. Пустой или повторный `userId` возвращает HTTP 400.

Выполните команды из корня репозитория. После создания воркфлоу подставьте его UUID в `WORKFLOW_ID` и задайте новые UUID в `RUN_ID` и `EVENT_ID`. Повторный `eventId` с тем же содержимым возвращает текущее состояние. Повторный `runId` с теми же параметрами работает так же.

```sh
curl -fsS "http://127.0.0.1:8081/v1/workflow" \
  -H 'Content-Type: application/json' \
  -d '{"serviceId":"00000000-0000-0000-0000-000000000101"}'

curl -fsS "http://127.0.0.1:8081/v1/workflow/$WORKFLOW_ID/bulk/block" \
  -H 'Content-Type: application/json' \
  --data-binary @docs/workflow/workflow.example.json

curl -fsS "http://127.0.0.1:8080/api/workflow/runs" \
  -H 'Content-Type: application/json' \
  -d "{\"runId\":\"$RUN_ID\",\"workflowId\":\"$WORKFLOW_ID\",\"entryBlockId\":\"voice.start\"}"

curl -fsS "http://127.0.0.1:8080/api/workflow/runs/$RUN_ID/events" \
  -H 'Content-Type: application/json' \
  -d "{\"eventId\":\"$EVENT_ID\",\"text\":\"Привет, Александр!\"}"
```

После первого запроса на запуск состояние будет `waiting_message`. Последний запрос продолжит сценарий и вернёт `completed` с сообщением, которое ссылается на результат симуляции озвучки. `GET /api/workflow/runs/{runId}` возвращает то же сохранённое состояние.

Прототип обрабатывает события адресно по `runId` и держит одну активную точку ожидания на запуск. Оплата и генерация симулируются, а сформированные сообщения доступны в ответе API. Реальные файлы, доставка в канал и RabbitMQ потребуют подключения внешних адаптеров.

Для проверки двух сервисов с настоящим Postgres укажите `TEST_DATABASE_URL` с мигрированной тестовой базой и выполните `go test ./...` из `modules/scenario`. Интеграционный тест создаёт отдельного владельца и удаляет свои данные по завершении.

## Стенд

Из браузера можно проверить имя и окружение исполнителя через `GET /api/workflow/info` на хосте стенда. До введения аутентификации, ручки воркфлоу и запусков доступны внутри кластера. Для доступа нужен kubeconfig с контекстом стенда и правами на чтение этих Service, чтение и поиск Pod и создание `pods/portforward` в `system1-stage`. Убедитесь, что `kubectl config current-context` указывает на стенд. Право на открытие туннеля можно проверить командой `kubectl auth can-i create pods/portforward -n system1-stage`. Для HTTP-проверки откройте два локальных порта в отдельных терминалах. Исполнитель использует внутреннее имя `http://s1-workflow-validator` для связи с валидатором.

```sh
kubectl -n system1-stage port-forward svc/s1-workflow-validator 8081:80
kubectl -n system1-stage port-forward svc/s1-workflow 8080:80
```

Перед выкладкой примените миграции Flyway. `V0_0_4` создаёт таблицы валидатора, `V0_0_5` — таблицу запусков исполнителя. Настройте секреты в Vault для обоих сервисов.

| Сервис | Ключи секрета | Доступ к Postgres |
| --- | --- | --- |
| `s1-workflow-validator` | `DATABASE_URL` | Чтение `owners.services`, чтение и запись в `workflow_validator` |
| `s1-workflow` | `DATABASE_URL` | Чтение `owners.services`, чтение и запись в `workflow.runs` |
