# s1-flyway-migrations

GitHub Actions собирает и проверяет образ со всеми SQL из `db/postgres/migrations/`, публикует его в GHCR и передаёт digest шагу `Apply database migrations`. Шаг запускает один `batch/v1` Job в namespace окружения. Только `Complete=True` разрешает обновить рабочие теги сервисов, выполнить ArgoCD sync на SHA релиза и перезапустить Deployment. До этого тег `master`/`prod` не меняется даже при замене Pod или срабатывании CronJob. В PR и при ручном запуске workflow выполняются проверки без выката. Job не входит в ArgoCD ApplicationSet, не повторяет неудачный Pod и удаляется автоматически через час после завершения.

## Подготовка окружений

Namespaces `system1-stage` и `system1`, `ClusterSecretStore/cluster-secret-store` и ExternalSecret `github-container-registry` из `iac/kubernetes/s1-env/pull-secret.yaml` должны существовать до первого запуска. Если namespace пустой, сначала подготовьте эти ресурсы без синхронизации приложений. GHCR pull secret должен давать доступ к `s1-flyway-migrations`, а `PACKAGES_TOKEN` — право публиковать этот образ.

В Vault создайте `uno/system1-stage/s1-flyway-migrations` и `uno/system1/s1-flyway-migrations`. В каждом нужны `FLYWAY_URL` (JDBC URL целевой БД, без логина и пароля), `FLYWAY_USER` и `FLYWAY_PASSWORD`. Используйте отдельного миграционного пользователя для каждой БД, не суперпользователя. Ему нужны `CONNECT` и `CREATE` на целевую базу, `USAGE` и `CREATE` на `public`, а также владение создаваемыми объектами для последующего DDL. Права сервисных пользователей выдаются отдельно под их схемы и запросы; Job их не выдаёт. Pod должен иметь сетевой доступ к Postgres.

У kubeconfig из `KUBESECRET` нужны namespace-scoped права на создание, чтение и patch ExternalSecret миграций, чтение и наблюдение за двумя ExternalSecret, создание, чтение и удаление Job, чтение и список Pod и событий для диагностики, `get` на `pods/log` а также `get`, `list`, `watch` и `patch` для Deployment. Не выдавайте доступ к чтению значений Secret ради этого скрипта. ArgoCD должен оставаться без автоматического sync для этих приложений: ручной sync в обход workflow не ждёт Job. До первой раскатки примените обновлённый ApplicationSet из `iac/system1.yaml`: политика `create-update` должна действовать для контроллера, а существующие Application не должны иметь каскадных `resources-finalizer.argocd.argoproj.io` finalizers. Проверьте это отдельно: политика контроллера может иметь приоритет над настройкой ApplicationSet. Вывод приложения из эксплуатации после этого — отдельная операция, не удаление каталога из Git.

## Ошибки и повторный запуск

При сбое workflow не синхронизирует приложения. Смотрите вывод Flyway и состояние Job: имя печатается при ошибке. После исправления окружения повторите запуск того же актуального релиза; не перезапускайте старый релиз поверх более нового. Успешно применённые SQL Flyway повторно не исполняет. История — `public.flyway_schema_history`; автоматический `baseline`, `repair` и `clean` не запускаются. Не изменяйте уже опубликованные SQL. Перед первым релизом убедитесь, что бизнес-таблицы из начальных миграций отсутствуют. Изменения схемы должны быть совместимы со старой версией сервисов, пока проходит их rollout.

Push-релизы сериализованы по окружению. GitHub Actions может заменить ожидающий run более новым, поэтому каждый push-релиз пересобирает все образы для своего окружения, а не только файлы из diff последнего push. Для stage принимается текущая вершина `master`, для prod — самый новый `v*` по версионной сортировке Git. Не перемещайте опубликованные теги. После миграции рабочие теги `master`/`prod` получают digest образа, собранного этим запуском. Не запускайте выкаты вручную во время релиза. Если API был недоступен и отмену Job подтвердить не удалось, перед повтором проверьте, что этот Job и его Pod завершились.

Локально сценарии Job и граф workflow проверяются командой `python3 iac/jobs/s1-flyway-migrations/tests/test_release.py` (нужен PyYAML). CI дополнительно запускает тот же образ дважды на временном PostgreSQL 16 и сверяет количество успешных миграций.
