# s1-flyway-migrations

GitHub Actions собирает и проверяет образ со всеми SQL из `db/postgres/migrations/`, публикует его в GHCR и передаёт digest шагу `Apply database migrations`. Шаг запускает один `batch/v1` Job в namespace окружения. Только `Complete=True` разрешает ArgoCD sync на SHA релиза и перезапуск Deployment. В PR и при ручном запуске workflow выполняются проверки без выката. Job не входит в ArgoCD ApplicationSet, не повторяет неудачный Pod и удаляется автоматически через час после завершения.

## Подготовка окружений

Namespaces `system1-stage` и `system1`, `ClusterSecretStore/cluster-secret-store` и ExternalSecret `github-container-registry` из `iac/kubernetes/s1-env/pull-secret.yaml` должны существовать до первого запуска. Если namespace пустой, сначала подготовьте эти ресурсы без синхронизации приложений. GHCR pull secret должен давать доступ к `s1-flyway-migrations`, а `PACKAGES_TOKEN` — право публиковать этот образ.

В Vault создайте `uno/system1-stage/s1-flyway-migrations` и `uno/system1/s1-flyway-migrations`. В каждом нужны `FLYWAY_URL` (JDBC URL целевой БД, без логина и пароля), `FLYWAY_USER` и `FLYWAY_PASSWORD`. Используйте отдельного миграционного пользователя для каждой БД, не суперпользователя. Ему нужны `CONNECT` и `CREATE` на целевую базу, `USAGE` и `CREATE` на `public`, а также владение создаваемыми объектами для последующего DDL. Права сервисных пользователей выдаются отдельно под их схемы и запросы; Job их не выдаёт. Pod должен иметь сетевой доступ к Postgres.

У kubeconfig из `KUBESECRET` нужны namespace-scoped права на создание, чтение и patch ExternalSecret миграций, чтение и наблюдение за двумя ExternalSecret, создание, чтение и удаление Job, чтение и список Pod и событий для диагностики, `get` на `pods/log` и существующие права перезапуска Deployment. Не выдавайте доступ к чтению значений Secret ради этого скрипта. ArgoCD должен оставаться без автоматического sync для этих приложений: ручной sync в обход workflow не ждёт Job.

## Ошибки и повторный запуск

При сбое workflow не синхронизирует приложения. Смотрите вывод Flyway и состояние Job: имя печатается при ошибке. После исправления окружения повторите запуск того же актуального релиза; не перезапускайте старый релиз поверх более нового. Успешно применённые SQL Flyway повторно не исполняет. История — `public.flyway_schema_history`; автоматический `baseline`, `repair` и `clean` не запускаются. Не изменяйте уже опубликованные SQL. Перед первым релизом убедитесь, что бизнес-таблицы из начальных миграций отсутствуют. Изменения схемы должны быть совместимы со старой версией сервисов, пока проходит их rollout.

Push-релизы сериализованы по окружению. GitHub Actions может заменить ожидающий run более новым, поэтому каждый push-релиз пересобирает все образы для своего окружения, а не только файлы из diff последнего push. Образы сервисов пока остаются на существующих тегах `master`/`prod`; только образ миграций передаётся по digest. Не запускайте выкаты или перезапуски вручную во время активного релиза.

Локально сценарии Job и граф workflow проверяются командой `python3 iac/jobs/s1-flyway-migrations/tests/test_release.py` (нужен PyYAML). CI дополнительно запускает тот же образ дважды на временном PostgreSQL 16 и сверяет количество успешных миграций.
